# Версии, обновления и CI/CD

Всё на этой странице работает на вашем собственном сервере и сохраняется в локальных файлах (`data/versions.json` и `data/git-integrations.json`). Внешних сервисов и привязанных аккаунтов нет: единственное, что вам нужно, — это GitHub, который вы и так используете для сборки.

## Версионирование

Каждая сборка несёт `versionName` и `versionCode`. Версия принимает от одного до четырёх числовых блоков, разделённых точками (`1`, `1.0`, `1.0.1`, `1.0.1.2`), а всё, что не вписывается в этот формат, отклоняется с кодом `400`. `versionCode` — целое число, которое всегда растёт: Play Store требует, чтобы оно увеличивалось при каждой публикации, а сервер принимает любое положительное целое число.

В студии вы заполняете это на шаге «Приложение». Через API они передаются в теле `POST /api/build` как `versionName` и `versionCode`; в `POST /api/v1/build` они также принимаются.

## Публикация и запрос версий

```bash
curl -X POST /api/versions/publish -H "Content-Type: application/json" \
  -d '{"appId":"com.miempresa.miapp","version":"1.0.1","changelog":"Corrige audio en segundo plano"}'
# → {"ok":true,"appId":"com.miempresa.miapp","versions":[{"version":"1.0.1","changelog":"…","publishedAt":1712345678901}]}
```

Сохраняется до 20 записей на `appId`, причём самая новая всегда стоит первой. Если вы не передали `appId` или версия не соответствует формату, возвращается `400`.

```bash
curl /api/versions/com.miempresa.miapp
# → {"appId":"com.miempresa.miapp","versions":[…]}
```

Возвращается полный список. Если для данного `appId` ничего не публиковалось, отвечается пустым объектом (`versions: []`).

```bash
curl "/api/check-update?appId=com.miempresa.miapp&version=1.0.0"
# → {"updateAvailable":true,"latest":"1.0.1","changelog":"Corrige audio en segundo plano"}
```

Отправленная версия сравнивается с последней опубликованной по компонентам. Если опубликованного ничего нет, возвращается `{"updateAvailable":false}`.

Это реестр, который можно запросить: встроенного OTA-клиента в сгенерированном приложении нет, поэтому баннер «доступна новая версия» нужно реализовать самому — на вашем сайте или в вашем HTML, вызывая этот endpoint и давая ссылку на ваш APK или AAB.

## Автоматическая сборка при каждом push

Процесс состоит из четырёх шагов:

1. Подключите репозиторий: `POST /api/git/connect` с `{"repo":"usuario/mi-web","branch":"main"}`. Интеграция сохраняется, и возвращается её `id`.
2. Сгенерируйте workflow: `POST /api/cicd` с `{"repo":"usuario/mi-web","branch":"main","baseUrl":"https://tu-dominio.com"}`. Возвращается полный YAML и путь, куда его загрузить.
3. Загрузите этот YAML в `usuario/mi-web/.github/workflows/inteebuild-auto.yml`.
4. Каждый push в эту ветку запускает `curl` workflow на `POST /api/git/webhook` вашего сервера.

Webhook принимает нативный формат GitHub (`{"repository":{"full_name":"usuario/mi-web"},"ref":"refs/heads/main"}`), а также короткий формат с `repo` и `branch`. Если для этой комбинации нет зарегистрированной интеграции, возвращается `404`. Если в теле есть поле `config`, оно используется как конфигурация сборки; иначе создаётся минимальная с `url: https://usuario/mi-web` и именем репозитория.

Интеграции перечисляются через `GET /api/git/integrations` и удаляются через `DELETE /api/git/:id`.

Нюанс, который стоит знать перед отправкой токена: поле `token` в `connect` сохраняется целиком в `data/git-integrations.json` (помимо сводки для списка), и сейчас его никто не читает. Поскольку webhook его не использует, рекомендуется не отправлять его.

Поскольку автоматическая очистка удаляет ветки `build-*` сразу по истечении нескольких минут, репозиторий сборок не забивается: каждый push создаёт новую ветку, один запуск и несколько недолговечных артефактов.

О лимитах сборок — в [production.md](./production.md). О том, что получается в результате каждой сборки, — в [outputs.md](./outputs.md).
